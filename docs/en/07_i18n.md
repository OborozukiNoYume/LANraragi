# Internationalization (i18n)

> Baseline commit `2094cc1d` (2026-09-04). Facts verified against code — cite-checked at generation time.

## Overview

LANraragi translates its web UI at two levels with a single message catalog:

- **Backend / templates** — Template Toolkit files call the `c.lh()` helper, which resolves messages through a `Locale::Maketext` lexicon loaded from Gettext `.po` files in `locales/template/`.
- **Frontend / JavaScript** — there is **no static `public/js/i18n.js` file**. Instead, the server renders `templates/i18n.html.tt2` as JavaScript on the fly, so browser-side code receives the same translated strings without any client-side i18n library.

The user-facing workflow (Weblate, `.po` editing rules) is documented upstream in `tools/Documentation/extending-lanraragi/translations.md`.

## Backend: the Maketext lexicon

`lib/LANraragi/Utils/I18N.pm` subclasses `Locale::Maketext` and declares one lexicon per language via `Locale::Maketext::Lexicon`, using the `Gettext` format:

```perl
use Locale::Maketext::Lexicon {
    de      => [ Gettext => "../../locales/template/de.po" ],
    en      => [ Gettext => "../../locales/template/en.po" ],
    ...
    _auto   => 0,
};
```

- The `.po` paths are relative to the module's location on disk, pointing into `locales/template/`.
- `_auto => 0` turns off the Auto-lexicon fallback: a missing lookup raises an error instead of
  silently returning the key — which is exactly what the `lh` helper's eval + `en` retry catches
  (see below). Language selection is LANraragi's own logic because `get_handle` is always handed
  an explicit candidate list; `Locale::Maketext` never consults locale environment variables.
- Both modules are pinned in `tools/cpanfile`: `Locale::Maketext` 1.33 and `Locale::Maketext::Lexicon` 1.00.

### Unregistered `.po` files: Italian and Assamese

`locales/template/` contains 14 `.po` files, but only 12 are reachable:

- `locales/template/it.po` (Italian) and `locales/template/as.po` (Assamese) are **not registered** in `lib/LANraragi/Utils/I18N.pm`, so no language handle can load them and their translations never reach the UI.
- The language dropdown in `templates/templates_config/config_global.html.tt2` still offers an `it` (Italiano) option. Selecting it makes `get_handle` skip the unknown tag and land on the English fallback — the UI stays in English even though `it.po` exists in the tree.
- `as` is not offered in the dropdown at all.

In short: **12 languages are actually loadable**, and Italian is the one gap between the UI option list and the registered lexicon.

## Language negotiation

`lib/LANraragi/Utils/I18NInitializer.pm` registers the `lh` helper on the Mojolicious app; it is wired up during startup in `lib/LANraragi.pm` (`LANraragi::Utils::I18NInitializer::initialize($self)`). Resolution order inside the helper:

1. **Forced language** — the server-wide language setting is read once at startup via `$app->LRR_CONF->get_language` and stored as the `forced_language` app default (avoiding a Redis query per request). If it is set and not `auto`, it wins.
2. **`Accept-Language` header** — when set to `auto`, the request's `Accept-Language` is split on commas and quality values (`;q=0.8`) are stripped, preserving the browser's preference order.
3. **English fallback** — `en` is appended to the candidate list if absent.

The candidate list is passed to `LANraragi::Utils::I18N->get_handle(@langs)`, which returns the first loadable handle (this is what makes unsupported tags like `it` degrade to English). `maketext` is wrapped in `eval`: on error, the message is retried with the `en` handle, and if that also fails the raw message key is returned. Arguments are encoded to UTF-8 before translation and the result decoded back.

The forced-language setting lives in Redis config (default `auto`, see `get_language` in `lib/LANraragi/Model/Config.pm`) and is picked from the dropdown in `templates/templates_config/config_global.html.tt2`, which notes it is fully effective after a restart — consistent with the read-once-at-startup design.

### Request flow at a glance

For a single translated string, end to end:

1. A template calls `c.lh("Add Archives")`; the helper checks the `forced_language` stash default (set at startup).
2. If `auto`, the request's `Accept-Language` (e.g. `zh-TW,zh;q=0.8,en;q=0.3`) is parsed into `zh-TW`, `zh`, `en`.
3. `en` is appended if missing, and `LANraragi::Utils::I18N->get_handle(@langs)` picks the first language with a registered lexicon (`zh-tw` → `zh_Hant.po` in this example).
4. `$handle->maketext("Add Archives")` performs the lookup, with arguments UTF-8 encoded beforehand and the result decoded afterwards.
5. Any lookup error is caught, retried against the `en` handle, and ultimately the raw key is returned.

## Frontend: a server-generated JavaScript module

- `lib/LANraragi/Utils/Routing.pm` exposes `GET /js/i18n.js` (on the public route set, which means it also sits behind login when No-Fun Mode is enabled), dispatched to `i18_n#index`.
- `lib/LANraragi/Controller/I18N.pm` renders the `i18n` template with `Content-Type: application/javascript`.
- `templates/i18n.html.tt2` builds a `const I18N = {...}` object by interpolating `c.lh()` for every entry — 255 interpolations at the time of writing. Two entry shapes exist:

```javascript
I18N.SaveSuccess = "[% c.lh("Saved!") %]";
I18N.BatchSleeping = (x) => `[% c.lh("Sleeping for \${x} seconds.") %]`;
```

  Plain constants for static strings, arrow functions for strings that take runtime parameters (placeholders are filled in the browser via template literals).

- `templates/common/importmap.html.tt2` maps the bare module specifier `i18n` to `/js/i18n.js?$version` (the version query busts caches across releases). 19 modules under `public/js/` consume it with `import I18N from "i18n"`.

Because the file is rendered per request, browser-side strings always follow the same forced-language/Accept-Language negotiation as server-rendered pages.

## Template usage

Wrap user-visible text in `c.lh()` (20 templates under `templates/` use it):

```html
<a href="[% c.url_for("/upload") %]">[% c.lh("Add Archives") %]</a>
```

Placeholders in templates use Maketext bracket notation and trailing arguments:

```html
[% c.lh("Version [_1] [_2]", version, vername) %]
```

## Translation catalog

- `locales/template/en.po` is the source catalog: 639 message entries (640 `msgid` lines including the empty header), organized into 20 sections, one per template (including `i18n.html.tt2` for frontend strings). 19 sections are delimited by `# ------Start of ...------` comments; the i18n section's opening delimiter is misspelled in the catalog as `# ------Stary of i18n.html.tt2------`, so a `Start of` grep finds only 19. Two entries (`Rescan Archive Directory` and its help text) sit between the Upload and i18n sections, outside any delimiters.
- Each language keeps the same `msgid` keys; only `msgstr` values differ.

A typical slice of `locales/template/en.po`:

```
# ------Start of Backup.html.tt2------
msgid "Database Backup/Restore"
msgstr "Database Backup/Restore"

msgid "Restoring your backup ..."
msgstr "Restoring your backup ..."
# ------End of Backup.html.tt2------
```

In the English file `msgid` and `msgstr` are *usually* identical — exceptions include the JS
placeholder entries (`msgstr` drops the `\$` escape) and a few entries where `msgstr` adds markup
or whitespace (e.g. `Version %1 %2` becomes `Version %1 - %2`). Other languages diverge freely
while keeping the key byte-for-byte equal to what templates pass to `c.lh()`.

## Translation workflow

Translations are hosted on Weblate (badge in `README.md`, contributor guide in
`tools/Documentation/extending-lanraragi/translations.md`): contributions at `https://hosted.weblate.org/projects/lanraragi/lanraragi-source/` are committed back as pull requests against the GitHub repository.

To translate in-tree instead:

1. Copy `locales/template/en.po` to a new `<lang>.po` in `locales/template/` and translate the `msgstr` values, keeping `msgid` untouched.
2. Observe the placeholder conventions, which differ by surface:
   - HTML templates: `[_1]` in the template corresponds to `%1` in the `.po` entry.
   - JavaScript: the `msgid` in `i18n.html.tt2` and the `.po` file escapes the dollar (`\${title}`), while `msgstr` uses a literal `${title}`.
3. Keep HTML markup (`<br/>`, `<b>`, links) inside translated strings intact.
4. Match `msgid` **exactly** — a stray trailing space in a `c.lh()` call prevents the entry from matching any catalog key.
5. Mind the `~` quirk: `~` acts as an escape character in `Locale::Maketext`, so a `msgid` containing `~` will not match; keep `~` out of `msgid` and only inside `msgstr` (as done for the tag-syntax help string in `config_tags`).

Adding a string requires touching three places: the template (or `templates/i18n.html.tt2` for JS), a matching `msgid`/`msgstr` pair in `locales/template/en.po`, and eventually the other `.po` files.

## Adding a new language

1. Create `locales/template/<lang>.po` from `en.po`.
2. Register a handle in `lib/LANraragi/Utils/I18N.pm` pointing at the new file — **without this step the file is dead weight** (the current `it.po`/`as.po` situation).
3. Add an `<option>` to the language `<select>` in `templates/templates_config/config_global.html.tt2`.
4. Restart the server so the startup-time forced-language default is refreshed.

## Quirks and troubleshooting

- **A string stays in English although it is translated.** `msgid` matching is exact; a trailing space or different quoting inside `c.lh()` breaks the lookup, and unknown keys render as the key itself after the double fallback in `lib/LANraragi/Utils/I18NInitializer.pm`.
- **Selecting Italian yields English.** The dropdown offers `it` but no handle is registered (see above); `get_handle` skips it and lands on the appended `en`.
- **Forced language seems stale.** It is read once at startup into the `forced_language` default; a Redis config change only takes effect after a restart.
- **Locale environment variables are ignored.** `get_handle` in `lib/LANraragi/Utils/I18NInitializer.pm` is always given an explicit candidate list (forced setting, then `Accept-Language`, then `en`), so `Locale::Maketext` never performs its own environment detection; only those candidates matter.
- **Frontend strings behave inconsistently with the rest of the page.** They come from the same `/js/i18n.js` rendering, but browsers cache JavaScript — the importmap's `?$version` cache-buster exists precisely to invalidate that cache on upgrades.
- **The unknown-operation log line would crash.** The `BatchUnknownOperat` arrow function in `templates/i18n.html.tt2` interpolates `${oper}`, a variable its `(id, msg)` parameter list never defines — invoking it (which `batch.js` does when the server answers "Unknown operation type") raises a `ReferenceError` instead of rendering a message. Latent only: the stock UI sends just the five operations the server knows.
